# 第 1 章　引言

## 1.1　项目设计需求

### 1.1.1　研究背景

随着大语言模型（LLM）技术的快速发展与广泛应用，AI Agent（人工智能代理）正逐步成为人工智能应用的主流形态。AI Agent 能够自主感知环境、做出决策并执行动作，在智能问答、自动化办公、数据分析、内容生成等众多场景中展现出巨大潜力。然而，构建一个完整的 AI Agent 应用往往需要整合多个组件——包括 LLM 调用、工作流编排、外部工具调用、记忆管理、RAG（检索增强生成）等——这对开发者的技术能力提出了较高要求，也使得 AI 应用的开发效率受到制约。

当前市场上虽然已有一些工作流编排工具（如 LangFlow、ComfyUI、Dify 等），但在以下方面仍存在明显不足：

- **缺乏深度 LLM 集成**：多数工具仅支持简单的 API 调用，缺乏对 Agent 推理链、多模型协作、工具调用等高级能力的产品化支持；
- **可视化与灵活性的平衡欠佳**：部分工具要么过于简陋、缺乏可视化编辑器，要么过度封装导致灵活性不足；
- **实时性与可观测性薄弱**：工作流执行过程中的状态监控、日志追踪、异常告警等可观测性能力普遍缺失；
- **多租户与团队协作能力不足**：难以满足企业级团队协作与多项目管理的需求。

### 1.1.2　设计目标

本项目旨在设计并实现一个名为 **Flowly** 的 AI Agent 工作流编排平台，其核心设计目标如下：

1. **可视化工作流编辑器**：提供基于拖拽的可视化编辑器，使用户能够通过图形化方式构建复杂的工作流，无需编写代码即可完成从简单到复杂的 AI 自动化流程设计；
2. **多模型 LLM 网关**：支持 OpenAI GPT 系列、Anthropic Claude 系列及自定义 LLM 端点的灵活接入，通过统一网关屏蔽底层差异；
3. **AI Agent 生命周期管理**：支持创建、配置、调试和部署 AI Agent，提供丰富的内置工具和自定义工具扩展能力；
4. **自然语言生成工作流**：支持用户以自然语言描述需求，系统自动将其转化为可执行的工作流草图，降低使用门槛；
5. **实时执行监控**：通过 WebSocket 实现工作流执行过程的实时推送，配合日志系统和告警机制，保障系统可观测性；
6. **RAG 知识增强**：提供完整的检索增强生成管线，支持向量数据库、文档解析和语义检索，为 Agent 提供知识支撑；
7. **多租户与团队协作**：基于多租户架构设计，支持团队成员权限管理与工作流共享。

### 1.1.3　设计约束与可行性分析

本项目在设计中面临以下约束条件，并做出了相应的可行性分析：

- **技术栈选型约束**：需要在保证功能完整性的前提下，选择学习曲线适中、生态成熟的技术栈。前端选用 Vue 3 + Vite，后端选用 Django 5，均为业界主流框架，社区资源丰富；
- **开发时间约束**：课程时间为 2026.4.20—2026.4.30（约 10 天），需优先实现核心功能（工作流编辑器、Agent 管理、执行引擎），非核心功能可采用迭代方式后续完善；
- **成本约束**：优先使用开源技术栈，LLM 调用采用 API 模式无需额外基础设施投入，数据库采用 Docker 容器化部署，开发测试成本可控。

综合分析，上述设计目标在技术层面和资源层面均具备可行性。

- **可用性需求**：系统整体可用性目标 ≥ 99%（SLA），前端提供友好的错误提示和加载状态，避免用户操作丢失；

- **可扩展性需求**：节点类型支持插件化扩展，新增节点类型无需修改核心代码；LLM 网关支持新模型商接入；
- **可维护性需求**：前后端代码遵循统一的编码规范，API 契约通过 OpenAPI 规范文档化管理，核心模块具备单元测试覆盖。

### 2.2.1　前端技术选型

前端选用 **Vue 3** 作为核心框架，主要基于以下考虑：

## 2.4　设计实现方案

### 2.4.1　系统架构设计

Flowly 平台采用**分层架构**设计，从上至下分为四个层次：

```
┌─────────────────────────────────────────────┐
│           Presentation Layer (前端)            │
│  Vue 3 + Vite + Element Plus + Vue Flow      │
├─────────────────────────────────────────────┤
│            Business Layer (后端)               │
│  Django REST Framework + Django Channels      │
│  LangChain / LangGraph / Celery               │
├─────────────────────────────────────────────┤
│              Data Layer                       │
│  MySQL 8.0 + Redis 7 + 向量数据库             │
├─────────────────────────────────────────────┤
│           Infrastructure Layer                 │
│  Docker + Nginx + Linux                       │
└─────────────────────────────────────────────┘
```

**前后端通信机制：**

- **HTTP REST API**：所有 CRUD 操作通过 RESTful API 完成，由 Axios 封装调用；
- **WebSocket**：工作流执行日志、Agent 对话流式输出通过 WebSocket 实时推送（基于 Django Channels + Redis）；
- **Celery + Redis**：耗时任务（工作流执行、文档解析、向量生成）通过 Celery 异步处理，结果通过 WebSocket 回调推送。

**数据流设计：**

```
用户操作 → 前端状态 → REST API → Django Views → ORM → MySQL
                              ↓
                         LangChain
                              ↓
                         LLM API (OpenAI/Claude)
                              ↓
                         Celery Task
                              ↓
                         WebSocket → 前端实时展示
```

### 2.4.2　数据模型设计

核心数据模型设计如下：

**Tenant（租户）：** 多租户隔离，每个租户拥有独立的用户、工作流和 Agent。

**User（用户）：** 继承自 Django 内置 User 模型，关联 Tenant，支持 JWT 认证。

**Workflow（工作流）：** 核心实体，存储工作流元数据（名称、描述、版本）、工作流定义（JSON 格式的 DAG 结构）、状态（草稿/已发布/已归档）和执行统计。

**WorkflowNode（工作流节点）：** 工作流中的节点定义，包含节点类型、位置坐标、配置参数（JSON）、输入输出映射。

**WorkflowExecution（工作流执行记录）：** 每次执行的记录，包含输入参数、执行状态、开始/结束时间、结果输出、错误信息。

**Agent（AI Agent）：** Agent 元数据，包括名称、描述、LLM 配置（模型选择、参数）、系统提示词、内置工具集。

**AgentTool（Agent 工具）：** 可复用的工具定义，支持 HTTP 调用、代码执行、内置操作等类型。

**NLWorkflowSession（自然语言生成会话）：** 自然语言生成工作流的会话上下文，保存用户意图和生成的中间结果。

**VectorStore（向量知识库）：** 知识库存储，支持多种向量数据库后端。

**APIKey（API 密钥）：** 用于第三方系统集成的 API Key 管理。

### 2.4.3　关键算法设计

**工作流 DAG 解析算法：**

工作流以有向无环图（DAG）形式存储，节点表示操作步骤，边表示数据流向。执行引擎通过拓扑排序确定节点执行顺序：

1. 从"开始节点"出发，递归遍历所有连接的节点，构建邻接表；
2. 计算每个节点的入度（in-degree）；
3. 使用 Kahn 算法进行拓扑排序，生成执行队列；
4. 按执行队列顺序调度节点，节点间通过异步 Future 等待依赖完成；
5. 支持条件节点和路由节点的分支逻辑，根据执行结果动态选择后续路径。

**自然语言生成工作流算法：**

基于 ReAct（Reasoning + Acting）模式设计：

1. **意图理解**：将用户自然语言输入发送给 LLM，附带结构化的提示词模板，要求 LLM 输出 JSON 格式的工作流草图（节点列表、节点类型、节点参数、连接关系）；
2. **草图预览**：将生成的工作流草图在前端可视化编辑器中展示，供用户确认和调整；
3. **确认转正式**：用户确认后，将草图保存为正式工作流，支持进一步编辑。

```
  │
  ├─── LLM 节点 ──▶ 调用 LLM 网关 ──▶ 流式/非流式结果
  ├─── HTTP 节点 ──▶ 执行 HTTP 请求 ──▶ 解析响应
  ├─── 条件节点 ──▶ 条件判断 ──▶ 选择分支路径
  ├─── 循环节点 ──▶ 迭代执行子图 ──▶ 聚合结果
  ├─── 代码节点 ──▶ Python Sandbox 执行 ──▶ 返回输出
  ├─── 延时节点 ──▶ 等待指定时间 ──▶ 继续执行
  └─── 其他节点 ──▶ 相应处理逻辑
  │
  ▼
节点结果写入上下文
  │
  ▼
检查是否有后续节点 ──▶ 有 ──▶ 取下一节点 ──▶ (循环)
  │
  ▼
无后续节点
  │
  ▼
聚合执行结果 ──▶ WebSocket 推送完成 ──▶ 记录执行日志
  │
  ▼
结束
```

### 2.5.3　Agent 对话流程

```
用户输入消息
     │
     ▼
Agent 接收消息 ──▶ 加载历史上下文
     │
     ▼
构建提示词 ──▶ 系统提示词 + 历史对话 + 当前输入
     │
     ▼
调用 LLM ──▶ 流式生成响应
     │
     ▼
检查工具调用 ──▶ 是 ──▶ 执行工具 ──▶ 结果回填 ──▶ 继续生成
     │
     ▼
否
     │
     ▼
返回最终响应 ──▶ 保存对话历史
     │
     ▼
前端流式展示
```

### 3.1.3　LLM 网关设计

LLM 网关（`gateway/` App）是系统对接大语言模型的核心抽象层，采用**策略模式**设计，支持多种 LLM 提供商的热切换：

```python
# 策略接口
class LLMProvider(ABC):
    @abstractmethod
    def chat(self, messages: list[dict], **kwargs) -> LLMResponse: ...
    
    @abstractmethod
    def stream_chat(self, messages: list[dict], **kwargs) -> Iterator[str]: ...

# OpenAI 实现
class OpenAIProvider(LLMProvider):
    def __init__(self, api_key: str, model: str = "gpt-4"):
        self.client = OpenAI(api_key=api_key)
        self.model = model

# Anthropic 实现
class AnthropicProvider(LLMProvider):
    def __init__(self, api_key: str, model: str = "claude-3-opus"):
        self.client = anthropic.Anthropic(api_key=api_key)
        self.model = model
```

网关服务通过配置中心的 `LLMProviderConfig` 动态注册提供商，用户可在 Agent 配置中选择使用的模型，网关自动路由到对应提供商。

## 3.2　模块设计

### 3.2.1　模块一：可视化工作流编辑器

可视化工作流编辑器是本项目最核心的前端模块，基于 **Vue Flow** 实现，提供类 Figma/Figma 的流畅编辑体验。

**核心功能：**

- 支持拖拽节点库中的节点到画布；
- 节点之间通过拖拽连线建立数据流向关系；
- 选中节点后弹出配置面板，设置节点参数；
- 支持多选、复制、粘贴、删除节点；
- 支持画布缩放（鼠标滚轮）、平移（鼠标中键拖拽）；
- 支持撤销（Ctrl+Z）和重做（Ctrl+Y），基于命令模式实现；
- 支持工作流草稿自动保存（每 30 秒）；
- 支持全屏编辑模式和节点搜索定位。

**节点类型实现：**

每种节点类型对应一个 Vue 组件，继承自 `CustomNode` 基类，通过 `node-type` 属性标识：

| 节点类型 | 组件名 | 核心配置 |
|---------|--------|---------|
| 开始节点 | StartNode | 无输入，只有一个输出端口 |
| 结束节点 | EndNode | 无输出，多个输入端口 |
| 输入节点 | InputNode | 参数名称、类型（文本/数字/文件） |
| 输出节点 | OutputNode | 输出字段映射 |
| LLM 节点 | LLMNode | 模型选择、提示词、温度、最大 Token |
| HTTP 节点 | HttpNode | URL、方法（GET/POST）、请求头、请求体 |
| 条件节点 | ConditionNode | 条件表达式、多个分支输出 |
| 路由节点 | SwitchNode | 基于字段值的 switch-case 分支 |
| 循环节点 | LoopNode | 迭代源、最大迭代次数、循环变量 |
| 变量节点 | VariableNode | 变量赋值与修改变量 |
| 提示词节点 | PromptNode | 提示词模板（支持变量插值） |
| 工具节点 | ToolNode | 选择已注册的 Agent 工具 |
| 代码节点 | CodeNode | Python 代码片段（沙箱执行） |
| 延时节点 | DelayNode | 延时时长（秒） |

### 3.2.2　模块二：工作流执行引擎

工作流执行引擎是后端核心模块，负责将工作流定义解析为可执行的任务队列，并通过 Celery 异步执行。

**执行流程：**

1. **DAG 验证**：校验工作流 DAG 无环、节点类型合法、必要端口已连接；
2. **拓扑排序**：按 Kahn 算法确定节点执行顺序；
3. **上下文初始化**：创建执行上下文（ExecutionContext），包含输入参数、全局变量、中间结果；
4. **节点调度**：按拓扑顺序启动各节点执行，使用 `asyncio` 实现节点级并发；
5. **结果聚合**：收集所有节点的输出，按结束节点汇总最终结果；
6. **日志写入**：每一步操作均写入执行日志，供监控和排障使用。

**节点执行器工厂：**

```python
class NodeExecutorFactory:
    @staticmethod
    def get_executor(node: WorkflowNode) -> NodeExecutor:
        executors = {
            'llm': LLMNodeExecutor,
            'http': HttpNodeExecutor,
            'condition': ConditionNodeExecutor,
            'code': CodeNodeExecutor,
            # ...
        }
        return executors.get(node.type, BaseNodeExecutor)()
```
