# 第 1 章　引言

## 1.1　项目设计需求

### 1.1.1　研究背景

随着大语言模型（LLM）技术的快速发展与广泛应用，AI Agent（人工智能代理）正逐步成为人工智能应用的主流形态。然而，构建一个完整的 AI Agent 应用往往需要整合多个组件——包括 LLM 调用、工作流编排、外部工具调用、记忆管理、RAG（检索增强生成）等——这对开发者的技术能力提出了较高要求，也使得 AI 应用的开发效率受到制约。

当前市场上虽然已有一些工作流编排工具（如 LangFlow、ComfyUI、Dify 等），但在以下方面仍存在明显不足：

- **缺乏深度 LLM 集成**：多数工具仅支持简单的 API 调用，缺乏对 Agent 推理链、多模型协作、工具调用等高级能力的产品化支持；
- **可视化与灵活性的平衡欠佳**：部分工具要么过于简陋、缺乏可视化编辑器，要么过度封装导致灵活性不足；
- **实时性与可观测性薄弱**：工作流执行过程中的状态监控、日志追踪、异常告警等可观测性能力普遍缺失；
- **多租户与团队协作能力不足**：难以满足企业级团队协作与多项目管理的需求。

### 1.1.2　设计目标

本项目旨在设计并实现一个名为 **Flowly** 的 AI Agent 工作流编排平台，核心设计目标如下：

1. **可视化工作流编辑器**：提供基于拖拽的可视化编辑器，使非技术用户也能构建复杂工作流；
2. **多模型 LLM 网关**：统一接入 OpenAI GPT、Anthropic Claude 系列模型；
3. **AI Agent 生命周期管理**：支持 Agent 的创建、配置、调试和部署；
4. **自然语言生成工作流**：用户以自然语言描述需求，系统自动生成工作流草图；
5. **实时执行监控**：通过 WebSocket 实现执行过程的实时推送；
6. **RAG 知识增强**：提供完整的检索增强生成管线；
7. **多租户与团队协作**：支持团队成员权限管理与工作流共享。

### 1.1.3　设计约束与可行性分析

- **技术栈选型**：前端 Vue 3 + Vite + Element Plus + Vue Flow，后端 Django 5 + DRF，均为业界主流框架；
- **开发时间**：课程时间为 2026.4.20—2026.4.30（约 10 天），优先实现核心功能；
- **成本约束**：优先使用开源技术栈，开发测试成本可控。

### 2.4.3　关键算法设计

**工作流 DAG 解析与拓扑排序算法：**

工作流以有向无环图（DAG）形式存储，节点表示操作步骤，边表示数据流向。执行引擎通过拓扑排序确定节点执行顺序：

1. 从"开始节点"出发，递归遍历所有连接的节点，构建邻接表；
2. 计算每个节点的入度（in-degree）；
3. 使用 Kahn 算法进行拓扑排序，生成执行队列；
4. 按执行队列顺序调度节点，节点间通过异步 Future 等待依赖完成；
5. 支持条件节点和路由节点的分支逻辑，根据执行结果动态选择后续路径。

```python
from collections import defaultdict, deque

def topological_sort(workflow_definition: dict) -> list[str]:
    """Kahn 算法拓扑排序，返回节点执行顺序"""
    nodes = workflow_definition['nodes']  # [{id, type, config}, ...]
    edges = workflow_definition['edges']   # [{source, target}, ...]

    # 构建邻接表和入度表
    in_degree = defaultdict(int)
    adjacency = defaultdict(list)
    node_ids = set()

    for node in nodes:
        node_ids.add(node['id'])

    for edge in edges:
        adjacency[edge['source']].append(edge['target'])
        in_degree[edge['target']] += 1
        if edge['source'] not in in_degree:
            in_degree[edge['source']] = 0

    # BFS: 从入度为 0 的节点开始（通常为 start 节点）
    queue = deque([nid for nid in node_ids if in_degree[nid] == 0])
    result = []

    while queue:
        node_id = queue.popleft()
        result.append(node_id)
        for neighbor in adjacency[node_id]:
            in_degree[neighbor] -= 1
            if in_degree[neighbor] == 0:
                queue.append(neighbor)

    # 检测环（有环时 result 长度小于节点总数）
    if len(result) != len(node_ids):
        raise WorkflowValidationError("工作流存在环形依赖，无法执行")

    return result
```

```python
# workflows/services/workflow_executor.py
class WorkflowExecutor:
    def __init__(self, workflow: Workflow, execution: WorkflowExecution):
        self.workflow = workflow
        self.execution = execution
        self.context = ExecutionContext(execution.input_data)
        self.execution_order = []

    def validate(self) -> None:
        """校验工作流 DAG 的合法性"""
        definition = self.workflow.definition
        nodes = {n['id']: n for n in definition['nodes']}
        edges = definition['edges']

        # 1. 校验存在 start 和 end 节点
        node_types = [n['type'] for n in nodes.values()]
        if 'start' not in node_types:
            raise WorkflowValidationError("缺少开始节点")
        if 'end' not in node_types:
            raise WorkflowValidationError("缺少结束节点")

        # 2. 校验无环（通过拓扑排序）
        sorted_order = topological_sort(definition)
        if not sorted_order:
            raise WorkflowValidationError("工作流存在环形依赖")

        self.execution_order = sorted_order

    def execute(self) -> dict:
        """执行工作流"""
        self.validate()
        self.execution.status = 'running'
        self.execution.started_at = timezone.now()
        self.execution.save()

        executor_factory = NodeExecutorFactory()

        for node_id in self.execution_order:
            node = self._get_node(node_id)
            executor = executor_factory.get_executor(node)

            # 推送节点开始执行日志
            self._push_log(node_id, 'INFO', f"开始执行节点: {node_id}")

            try:
                result = executor.execute(self.context)
                self.context.set_node_output(node_id, result)
                self._push_log(node_id, 'INFO', f"节点执行成功: {node_id}")
            except Exception as e:
                self._push_log(node_id, 'ERROR', f"节点执行失败: {e}")
                self.execution.status = 'failed'
                self.execution.error_message = str(e)
                self.execution.completed_at = timezone.now()
                self.execution.save()
                raise

        self.execution.status = 'success'
        self.execution.output_data = self.context.get_output()
        self.execution.completed_at = timezone.now()
        self.execution.save()

        return self.execution.output_data
```

```python
class HttpNodeExecutor(BaseNodeExecutor):

        config = self.node['config']
        url = self._resolve(config['url'], context)
        method = config.get('method', 'GET')
        headers = self._resolve_dict(config.get('headers', {}), context)
```

### 3.2.3　模块三：执行上下文管理

```python
# workflows/services/context.py
class ExecutionContext:
    """执行上下文，管理节点间的数据传递"""

    def __init__(self, input_data: dict):
        self.variables = copy.deepcopy(input_data)  # 全局变量
        self.node_outputs = {}  # 各节点输出缓存
        self.metadata = {}  # 元数据（执行时间、Token 消耗等）

    def set_node_output(self, node_id: str, output: dict):
        self.node_outputs[node_id] = output
        # 如果节点声明了输出变量，更新全局变量
        if 'variable_name' in output:
            self.variables[output['variable_name']] = output.get('value')

    def get_node_output(self, node_id: str) -> dict:
        return self.node_outputs.get(node_id, {})

    def resolve(self, template: str) -> str:
        """解析模板中的变量占位符 {{variable.path}}"""
        for match in re.finditer(r'\{\{([^}]+)\}\}', template):
            path = match.group(1).strip()
            value = self._get_nested(path)
            template = template.replace(match.group(0), str(value))
        return template

    def _get_nested(self, path: str):
        """支持 a.b.c 形式的多层属性访问"""
        parts = path.split('.')
        if parts[0] == 'input':
            return self._get_nested_from_dict(self.variables, parts[1:])
        elif parts[0] == 'output' and len(parts) > 2:
            return self._get_nested_from_dict(self.node_outputs.get(parts[1], {}), parts[2:])
        return None
```

### 3.2.4　模块四：Celery 异步任务集成

```python
# workflows/tasks.py
from celery import shared_task
from celery.utils.log import get_task_logger

logger = get_task_logger(__name__)

@shared_task(bind=True, max_retries=3)
def execute_workflow(self, workflow_id: int, input_data: dict, execution_id: str):
    """Celery 异步工作流执行任务"""
    from workflows.models import Workflow, WorkflowExecution
    from workflows.services.workflow_executor import WorkflowExecutor

    try:
        workflow = Workflow.objects.get(id=workflow_id)
        execution = WorkflowExecution.objects.get(id=execution_id)

        executor = WorkflowExecutor(workflow, execution)
        result = executor.execute()

        return {'status': 'success', 'result': result}

    except WorkflowValidationError as e:
        logger.error(f"工作流验证失败: {e}")
        raise self.retry(exc=e, countdown=5)

    except Exception as e:
        logger.error(f"工作流执行异常: {e}")
        # 更新执行记录为失败状态
        WorkflowExecution.objects.filter(id=execution_id).update(
            status='failed', error_message=str(e)
        )
        raise
```

## 4.1　项目总结

本次课程设计历时约十天，从需求分析、方案设计到编码实现，完整地经历了一个中等规模全栈项目的开发流程。本人负责的 **工作流执行引擎模块**，基本完成了预定的核心功能需求。

### 4.1.1　主要成果

1. **工作流数据模型**：设计并实现了完整的工作流、节点、执行记录的数据模型（Django ORM），支持多租户隔离；
2. **工作流执行引擎**：设计并实现了基于 DAG 拓扑排序的工作流执行引擎，支持 14 种节点类型，每种节点对应独立的执行器；
3. **执行上下文管理**：实现了 ExecutionContext 上下文字典，支持节点间数据传递和变量解析；

5. **WebSocket 实时日志**：通过 Django Channels 实现了执行日志的实时推送，前端可实时看到每个节点的执行状态；
6. **版本管理与导入导出**：实现了工作流版本控制和 JSON 格式的导入导出功能。

### 4.1.2　存在的不足

1. **并行执行未实现**：当前执行引擎按拓扑顺序串行执行，未实现可并行节点（如无依赖的分支）的并行执行优化；
2. **错误恢复机制有限**：节点执行失败后的重试机制较为简单，缺少更细粒度的退避策略；
3. **断点调试不完善**：断点功能仅支持从头到断点，未支持单步执行和变量查看。

## 4.2　技术收获

1. **Django ORM 深度应用**：掌握了复杂关联查询（多租户过滤、外键跨 App 关联）、JSONField 存储 DAG 数据、事务管理（@transaction.atomic）等实践技巧；
2. **Celery 异步任务开发**：掌握了 Celery 的任务定义、队列配置、结果存储、任务链（chain）和任务组（group）等高级特性；
3. **Django Channels WebSocket**：理解了 ASGI 协议、WebSocket 握手、Channel Layer 群组广播等核心概念；
4. **DAG 算法实践**：深入实践了 Kahn 拓扑排序算法，理解了有向无环图在工程中的广泛应用；
5. **设计模式应用**：在执行引擎中应用了工厂模式（节点执行器工厂）、模板方法模式（基类 BaseNodeExecutor）、策略模式（不同节点类型不同策略）；
6. **API 规范化开发**：遵循 DRF ViewSet + Router 模式，理解了序列化器在数据验证和转换中的作用。

## 4.3　改进方向

1. **并行执行优化**：引入依赖图分析，将无依赖的节点并行调度执行，提升整体执行效率；
2. **更健壮的重试机制**：引入指数退避（Exponential Backoff）重试策略，支持按节点类型配置不同的超时和重试参数；

## 4.4　课程心得

本次课程设计让我深刻体会到了"工程"二字的分量。工作流执行引擎看似只是一个简单的节点遍历循环，实际上要考虑的问题非常多：节点类型的可扩展性、并发执行与串行执行的取舍、错误处理与恢复、日志追踪的完整性……每一个细节都需要仔细权衡。
