# 00 - 总览与下一阶段发展方向

> 生成时间：2026-06-05  
> 目的：不是重复列问题，而是基于当前代码现状，给出 **产品方向 + 架构方向 + 功能落地方向 + 业务闭环方向**。

---

## 一、先说结论：你现在的方向，不该再继续“堆功能”

从现有代码和审查结果看，项目已经具备一个很明确的雏形：

- 它不是单纯的工作流编辑器；
- 它也不是单纯的模板市场；
- 它更接近一个 **面向团队与租户协作的 AI Workflow Platform**。

也就是说，这个项目真正应该发展的方向，不是“再多几个页面、再多几个接口”，而是把它打造成下面这条主线：

### 核心产品主线
**工作流定义 → 模板沉淀 → 团队复用 → 执行观测 → 成本治理 → 权限隔离 → 市场分发**

这是你现在代码里已经隐约出现、但还没有真正打通的业务链路。

当前最大的问题不是没有功能，而是：

1. **同一业务有多套真相源**；
2. **同一资源有多套权限语义**；
3. **同一动作在前后端有多套协议**；
4. **同一能力（模板/凭证/计费/执行日志）被拆成多个平行实现**。

所以，下一步正确方向不是继续横向扩展，而是纵向打通主链路。

## 二、结合代码现状，你这个项目最合理的产品定位

## 1. 产品定位建议
建议把 Flowly 定义为：

### 定位 A：团队级 AI 工作流平台
适合内部自动化、数据流、AI 编排、工具调用、知识检索、批处理、Agent 协作。

### 定位 B：可模板化、可运营化的工作流资产平台
工作流不只是“运行一次”，而是：
- 可以被沉淀成模板
- 可以被团队复用
- 可以被发布/精选/市场化
- 可以统计使用价值

### 定位 C：多租户可治理平台
如果你保留 tenant / member / credential / billing 这些能力，那你做的就不是 demo，而是 SaaS 雏形。

这意味着后续要重点建设的不是单页体验，而是这 6 个系统能力：

1. **定义系统**：编辑器、节点、边、变量、模板化
2. **执行系统**：执行器、日志、节点运行、重试、缓存
3. **资产系统**：模板、分类、收藏、评分、推荐
4. **治理系统**：权限、租户、成员、审计
5. **资源系统**：凭证、工具、模型、网关、知识库
6. **运营系统**：用量、成本、热门、推荐、发布审核

## 三、当前代码真实暴露出的发展瓶颈

下面这些不是抽象问题，而是我结合文档与代码抽样后，确认已经影响发展速度的瓶颈。

## 1. 模板系统已经阻塞产品增长
当前模板相关能力分散在：
- `Backend/templates`
- `Backend/marketplace`
- `Backend/workflows` 内嵌模板
- `Frontend/src/stores/marketplace.js`
- `Frontend/src/api/marketplace.js`
- `Frontend/src/api/workflow.js`

并且前端 `marketplace` store 仍然混用两套路由：
- 市场列表/安装走 `marketplaceApi`
- 从模板创建工作流走 `createFromTemplate` 的 workflow API

这说明：

### 你现在的模板业务并没有真正成为“资产系统”
它还停留在“多个实现临时共存”的阶段。

这会直接导致：
- 模板统计不可信
- 推荐排序不可信
- 用户心智混乱
- 后续做团队模板、审核流、商业化分发都会越来越痛苦

### 所以下一步最值得投入的主线之一：
**把模板系统升级为“工作流资产中心”**。

不是修页面，而是确立一条业务真相链：

**Workflow → Publish as Template → Review/Verify → Install/Use → Track Value → Recommend**

---

## 2. 多租户和权限还没形成“平台级规则”
从 `Backend/workflows/views.py` 的实现看，你已经开始补 `_get_accessible_tenant_ids()` 和 `_get_accessible_workflow_queryset()` 这种入口，这说明方向是对的。

但问题在于：

- 不是所有模块都复用这条规则；
- 还有很多模块仍然用 `owner=self.request.user` 这种单点过滤；
- 一些模块还在用不可靠的 `user.tenants.values_list(...)`；
- 前端与接口层仍然允许显式 tenant 语义流动。

这意味着现在的权限体系还不是“平台规则”，只是“局部补丁”。

### 你的产品一旦继续往团队协作方向发展，这块必须前置升级
否则后面所有团队功能都会变成安全债：
- 团队模板
- 团队知识库
- 团队凭证
- 团队 agent
- 团队计费
- 团队任务

### 正确方向
把“租户边界”和“资源归属”上升为统一规则：

- `owner` 表示创建者
- `tenant` 表示边界归属
- `visibility` 表示可见性
- `permission` 表示动作能力

如果不做这一步，后面你加的每个功能都会继续裂。

---

## 3. 前端当前最大问题不是 UI，而是领域边界失真
比如：
- `tenant` store 混着 tenant/member/skill/task/activity
- marketplace 页面非常重，逻辑过厚
- 前端对模板字段做大量兼容式 normalize
- workflow/template 状态协议还存在漂移

这说明前端当前不是“组件不够多”，而是：

### 前端没有按业务域建模
你现在前端更像“接口驱动的页面拼装”，还不是“领域驱动的界面系统”。

正确方向不是继续在单个页面里堆交互，而是把前端按业务域收敛成：

- workflow domain
- template domain
- execution domain
- tenant domain
- credential domain
- knowledge domain
- admin/ops domain

每个 domain 有自己的：
- API adapter
- store/composable
- type/DTO
- page/component

否则页面再做漂亮，业务还是会越来越乱。

## 四、你接下来最该补的功能，不是“更多”，而是“闭环”

下面是我认为最值得继续完善的功能和业务逻辑主线。

---

## 主线 A：把模板市场做成真正的“资产闭环”

这是你现在最有产品潜力的一条线。

## 目标
让模板从“静态展示”进化为“可沉淀、可分发、可追踪、可运营的资产”。

## 应补齐的业务能力

### 1. 模板生命周期
建议统一为：
- 草稿
- 待审核
- 已发布
- 已下线
- 已归档

当前很多地方还是 `is_public` / `is_published` / `is_active` 混杂，这不够表达真实业务。

### 2. 模板来源
建议明确模板来源：
- 官方模板
- 团队模板
- 个人模板
- 社区模板

这会直接影响：
- 权限
- 推荐排序
- 审核流程
- 展示标签

### 3. 模板使用路径
建议标准化：
- 预览模板
- 变量确认
- 凭证检查
- 知识库依赖检查
- 创建副本
- 安装成功引导
- 首次运行引导

你现在更多是“点一下就创建 workflow”，但真实业务里，模板可用性依赖很多前置资源。

### 4. 模板质量体系
建议增加：
- 模板评分
- 使用成功率
- 最近使用量
- 首次运行成功率
- 依赖完整度
- 官方认证/审核标记

这才是模板市场真正的排序基础。

### 5. 模板运营能力
建议增加：
- 精选位配置
- 模板推荐规则
- 新模板冷启动策略
- 分类页排序策略
- 热门模板算法
- 相似模板推荐

现在的市场更像展示页，还不是运营系统。

---

## 主线 B：把 workflow 做成“可执行、可观测、可回放”的生产能力

当前 `workflows` 的方向是对的，但还停留在结构过载阶段。

## 目标
把 workflow 从“可编辑”升级为“可稳定运行的业务执行单元”。

## 应补齐的业务能力

### 1. 执行观测闭环
建议统一执行侧能力：
- 执行总览
- 节点级状态流转
- 错误堆栈
- 输入输出快照
- token / cost 统计
- 重试记录
- cache 命中情况
- execution timeline

现在日志和执行明细口径分裂，不利于生产排障。

### 2. 执行控制能力
建议完善：
- 暂停 / 恢复
- 从失败节点继续
- 从指定节点重跑
- 跳过节点
- 人工确认节点
- 条件分支可解释

你如果想做企业级工作流，这些才是刚需。

### 3. 节点依赖与资源校验
在执行前增加 preflight：
- 是否缺凭证
- 是否缺知识库
- 是否缺模型权限
- 是否变量不完整
- 是否节点配置非法

不要等运行时报错才发现资源缺失。

### 4. 工作流版本体系
建议补齐：
- 草稿版本
- 已发布版本
- 运行绑定版本
- 模板导出版本
- 回滚版本

否则后面“模板来自哪个版本、运行到底跑的是哪个版本”会混乱。

---

## 主线 C：把凭证 / 模型 / 工具接入做成“资源中心”

这是未来能支撑复杂业务的基础层。

## 目标
让平台上的外部依赖不再散落在各 app 中，而是进入统一资源体系。

## 应补齐的业务能力

### 1. 统一凭证中心
区分但统一管理：
- 模型凭证
- API 凭证
- 工具凭证
- 第三方集成凭证

### 2. 统一资源绑定
工作流模板或工作流节点不直接绑死具体 key，而是引用：
- 凭证类型
- provider
- capability
- scope（个人/团队/系统）

### 3. 依赖检测
模板安装或工作流执行前能直接提示：
- 缺 OpenAI key
- 缺 Google Search 工具配置
- 缺某知识库权限
- 缺某租户共享资源

### 4. 成本治理
建议后面补：
- 按 workflow 统计成本
- 按 tenant 统计成本
- 按 template 统计成本
- 按 provider 统计成本
- 成本预警
- 预算上限

这决定它能不能往企业侧继续走。

---

## 主线 D：把知识库 / RAG / Agent 统一到 workflow 生态，不要各自为政

如果你后面还会继续做 RAG、Agent、Prompt、Dataset，那必须避免再复制出第四套系统。

## 正确方向
所有智能能力都应该作为 **workflow 的资源与节点生态** 来收敛，而不是平行产品。

### 建议统一原则
- Prompt 是节点资源，不是独立小孤岛
- Agent 是一种可配置执行单元，不是单独世界
- RAG/Knowledge 是知识资源，不是另一套权限体系
- Dataset 是数据资源，不是游离模块

### 对业务的价值
这样才能打通真实场景：
- 从模板一键生成客服 Agent 工作流
- 工作流绑定知识库与模型
- 执行结果回写分析
- 模板基于实际成功率继续优化

这才是平台化。

## 五、结合当前代码，我建议你的中期路线图

下面不是技术任务单，而是更接近“产品 + 架构”的三阶段路线。

## 阶段 1：止血期（1-3 周）

## 核心目标
先把系统从“继续长歪”拉回“可以稳定演进”。

## 必做事项

## 这一阶段不要做的事

- 不要再新建一套凭证配置页

---

## 阶段 2：收敛期（3-6 周）

## 核心目标
把重复系统收成真正的业务域。

## 必做事项
1. 建立 template domain
2. 建立 credential/resource domain
3. 建立 execution observability domain
4. 建立统一 DTO / serializer / frontend adapter
5. 建立统一 tenant permission mixin / policy
6. 建立前端按 domain 分层的 store + api + view 模式

## 成果标志
到这一步，你的系统应该做到：
- 模板只有一条主资源线
- 执行只有一条主观测线
- 凭证只有一个主入口
- tenant 只有一种主边界规则

---

## 阶段 3：增长期（6-12 周）

## 核心目标
在统一底座上，开始做真正有业务价值的能力。

## 最值得做的功能

### 1. 模板运营能力
- 推荐
- 精选
- 审核
- 相似模板
- 类目专题

### 2. 企业协作能力
- 团队共享模板
- 团队共享凭证
- 团队共享知识库
- 成员角色与审批

### 3. 执行治理能力
- 成本预警
- SLA / 失败告警
- 失败重试策略
- 执行审计与对账

### 4. 智能辅助能力
- 基于自然语言创建 workflow
- 基于历史执行推荐优化
- 基于模板使用率推荐组合节点

## 六、你这个方向该怎么“完善功能和业务逻辑”

我直接给结论，不绕。

## 1. 从“页面功能”思维切换到“业务闭环”思维
错误做法：
- 缺什么页面补什么页面
- 缺什么按钮补什么按钮
- 某个模块缺什么字段就地兼容一下

正确做法：
先问每条业务链是不是闭环：

### 模板闭环
是否具备：
- 创建
- 预览
- 依赖检查
- 安装/生成
- 首次运行
- 统计
- 评分
- 推荐
- 下线/归档

### 执行闭环
是否具备：
- 提交
- 校验
- 执行
- 观测
- 报错
- 重试
- 回溯
- 成本归集

### 团队闭环
是否具备：
- 加入租户
- 角色授权
- 访问资源
- 共享模板
- 共享凭证
- 操作审计

如果闭环不完整，就不要急着加外围功能。

---

## 2. 从“字段兼容”切换到“领域模型统一”
现在很多地方靠别名、normalize、兼容字段在撑着。
这只能短期止血，不能长期发展。

你接下来应该推动：
- 统一模板 DTO
- 统一 workflow DTO
- 统一 execution DTO
- 统一 credential DTO
- 统一 tenant access policy

这是后续所有功能加速的前提。

---

## 3. 从“单用户工具”切换到“团队平台”思维
如果你继续保留这些模块：
- tenant
- member
- billing
- credential
- marketplace
- monitoring

那就必须接受一个事实：

### 你已经在做平台，不是在做单人玩具
那业务逻辑就必须围绕：
- 谁能看
- 谁能改
- 谁能执行
- 谁能共享
- 谁来付费
- 如何审计

这些平台问题不解决，功能越多，风险越大。
